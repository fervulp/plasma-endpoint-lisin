# LiSin v1 — план развития

Лёгкий локальный EDR на один ноутбук. Ядро: **osquery** (состояние снимками) +
**Tetragon/eBPF** (события в реальном времени) → **DuckDB** → **Qt/QML**.
Ветка `v1-migration`; `v0/` — референс-монолит.

**Фокус:** ИНВЕНТАРИЗАЦИЯ и НАБЛЮДАЕМОСТЬ своей системы — «что есть, что
происходит, как запустилось, чей бинарник, куда ходит». Детекты/алерты и
реагирование (блокировка) — ОТЛОЖЕНЫ (см. «Границы»).

**Интерфейс — только Qt/QML.** (Веб-вариант обдумывался и отклонён.)

**Правило работы (задано пользователем):** каждый шаг — сначала «ВНУТРИ»
(движок/API, не видно), потом «ВИДНО» (в GUI, можно открыть и проверить
глазами). Ниже каждая фаза так и разбита.

**Принципы:** всё через конвейер; логика в экспертизе (SQL/YAML), не в коде;
никакого хардкода данных; состояние — только про эту машину; вычисление — в
источнике/view-модели; один компонент на поведение (DRY); проверять рендером и
числами.

---

## Сделано
- Состояние (osquery→`v1.duckdb`): `processes` (+ user/cpu/mem/uptime/on_disk),
  `ports_owned` (с владельцем).
- События (Tetragon→`v1-events.duckdb`): exec/exit/connect/file. Нормализация —
  SQL-вьюха `events_norm`, **материализуется** в реальную таблицу `events`
  (запросы 1-20 мс вместо 0.5-1.5 с по вьюхе). Политики `v1/tetragon/policies/`.
- Интерфейс (QML): Data (общие QueryBar+DataTable), Dashboards→Process (дерево:
  потребление + Σ ветка + uptime), **Pipelines** (потоки: точка входа → таблица →
  вьюха, с живыми числами; строятся ИЗ экспертизы, клик по этапу открывает
  правило), Expertise.
- Ядро дедуплицировано в `core/db.py`; мёртвый код QML вычищен.

## Фаза 1 — Обогащение событий (смысл вместо голых полей)
**Внутри:**
- SQL-вьюха/материализация `events ⋈ processes` (`ATTACH v1.duckdb AS state
  (READ_ONLY)` в events-соединение, либо копия `processes`) → пакет/пользователь/
  юнит процесса, которых в самом событии нет.
- ASN/владелец внешних адресов — как ВХОД конвейера (не спрятанный сетевой
  вызов).
- Новые трейс-политики: `execve` с аргументами, `setuid/setgid`, загрузка
  модулей ядра.

**Видно:** в ленте событий колонки «пакет/пользователь процесса», «владелец
адреса (ASN/страна)»; фильтр по ним; событие читается «кто (какой пакет) → что
→ куда (чей адрес)».

## Известные отличия от v0 (следствие перехода на osquery)
- **Браузеры**: osquery смотрит только СТАНДАРТНЫЕ пути профилей (`~/.mozilla`,
  chromium-семейство в `~/.config`). v0 искал профили по следам на диске
  (`places.sqlite`/`History`) и поэтому находил Zen, LibreWolf, Chromium внутри
  BurpSuite, flatpak-профили в `~/.var/app`. Пустая половина таблицы означает
  «в стандартных путях ничего», а не «не установлено». Вернуть покрытие можно
  только точкой входа на команде (как в v0) — решение отложено.
- **Без root** ряд таблиц законно пуст (iptables, shadow, чужие профили и
  history). Такие входы оставлены и honestly описаны в поле description.

## Фаза 2 — Больше состояния (перенос источников v0) — СДЕЛАНО (35 точек входа)
**Внутри:** источники v0 переписаны как osquery-входы. Каждый проверен на живой
системе (строки/колонки/время), у каждого свой `interval:` — инвентарь не
перечитывается на такте процессов. Готово: users, user_groups, sessions,
services (systemd_units), scheduled (crontab), startup_items, network,
net_config, dns, arp, ssh_keys, authorized_keys, sudoers, suid_binaries,
kernel_modules, kernel_params, security, system, cpu, memory,
browser_extensions. В работе: applications (rpm+pip+npm+vscode), sockets
(established-соединения!), storage/mounts/devices, open_files, shell_history,
containers, firewall, logins, uptime, ulimits.

**Видно:** новые вкладки в Data появляются САМИ (схема выводится из данных,
порядок — investigation-first в `tabPrio`).

**Дальше по этой фазе:** связи между таблицами (рёбра/вьюхи `_edges`) —
sockets↔processes, services↔applications, suid↔applications.

## Границы (осознанно НЕ делаем сейчас)
- **Детекты / алерты / корреляция** — «создание алертов» отложено. Упор на
  инвентаризацию и наблюдаемость, а не на срабатывания.
- **Реагирование (enforcement)** — блокировка процессов/файлов/сессий (Tetragon
  Sigkill/override) отложена. Сейчас только наблюдаем.
- **Веб-интерфейс** — не нужен, всё на Qt.
- **LLM** — удалён, не возвращаем.
- **Внешние фиды угроз** (C2/Tor) — устаревают за часы; CVSS по своим пакетам
  можно вернуть как ВХОД.
- **Правка ячеек состояния** — снимок osquery перезапишется; связи выражаем
  SQL/графом, не join-билдером.

## Проверка (обязательна после каждой правки)

    systemctl --user stop lisin.service      # приложение держит лок на БД
    cd v1 && PYTHONNOUSERSITE=1 python3 tests/run.py

`tests/run.py` — четыре секции, выход ненулевой при любой поломке:
- **compile** — все .py импортируются, все .qml разбираются;
- **engine** — полный принудительный сбор: каждая точка входа работает, каждая
  вьюха применяется, цикл укладывается во время, временные файлы убраны;
- **data** — сколько колонок пусты во ВСЕХ строках (источник сломался молча);
- **paths** — по КАЖДОЙ вкладке: свободный поиск, условие, сортировка,
  группировка и инвариант «SELECT = то, что показывает таблица», плюс отсутствие
  рантайм-предупреждений QML.

Почему именно так: компиляция доказывает, что QML разбирается, рендер — что он
раскладывается; ни то, ни другое не нажимает кнопку. Найденные дефекты были
третьего рода — запрос, который интерфейс строит, база отвергает на какой-то
таблице, или значение переносится с предыдущей вкладки. Это видно только если
пройти путями.

## Инварианты производительности (держать)
- События читаются из **материализованной таблицы**, НЕ сканом json-вьюхи
  (иначе count/фильтр по 300k = секунды и подвисание UI на каждом пуше).
- Счётчики вкладок и пуши снимка — по реальным таблицам (мс), не по тяжёлым
  вьюхам.
- Любой запрос на тик/переключение вкладки держать в единицах-десятках мс;
  замерять при изменении.
- **Ячейка таблицы = ОДИН объект.** Значение — плоский `Text` (не `QQC2.Label`),
  цвет/шрифт спускаются с таблицы. Ничего «тяжёлого и скрытого» в каждой ячейке:
  ни `Kirigami.Icon`/`CheckBox` под `visible:false`, ни `HoverHandler`, ни
  `Loader` — специальные колонки идут отдельным Repeater'ом, а действия при
  наведении рисует ОДИН оверлей на таблицу.
  (Замерено: 6 объектов/ячейку × 21 колонка = переключение вкладки ~6 с.)
- **Одна пересборка таблицы на переключение вкладки:** сначала очистить строки,
  затем сбросить состояние (запрос/сортировка/выделение), и ОДИН раз загрузить.
  Каждое промежуточное присваивание в `rows`/`columns` = полная пересборка
  делегатов.
- Замерять переключение харнессом (`setProperty("tabIndex")` + `processEvents`),
  а не на глаз: бэкенд может отвечать за 4 мс, а переключение занимать секунды.
- **Список колонок обязан быть стабильным по значению.** Каждый пуш приносит
  НОВЫЙ объект снимка, поэтому производные `cur/listCols/visibleCols` меняют
  идентичность даже когда данные те же. Если из них напрямую собирать `columns`
  таблицы — таблица целиком пересоздаётся каждые 3 с. Пересобирать только при
  изменении ПОДПИСИ (`syncColumns`).
- **Сборщик не держит лок БД на время подпроцесса.** osquery — это subprocess;
  UI читает через тот же лок, и удержание лока на весь цикл вешало окно.
  Сначала опросить (без лока), потом писать (под локом).
- **Тяжёлое содержимое закрытых панелей — под `Loader { active: open }`.**
  В QML закрытая панель это живое дерево объектов: список колонок строил по 5
  контролов на колонку и пересобирался на каждой смене вкладки.
- **Фоновые обновления — только для видимой страницы** (`if (view.visible)`) и с
  коалесингом по таймеру: страницы живут в кэше и продолжают обновляться, даже
  когда пользователь в другом разделе.
- **Никаких `add:`-переходов у таблицы**: строки заменяются целиком при каждом
  обновлении, и все они считаются «добавленными» — таблица мигает по таймеру.
- **Результат источника НЕ превращать в Python-объекты.** osquery отдаёт JSON —
  пусть DuckDB читает его сам (`read_json` из файла). Построчная вставка через
  `executemany` стоила 4 с на 4000 строк против 26 мс (155x); на 35 источниках
  это разница между циклом 75 с и 13 с.
- **У каждой точки входа свой `interval:`.** Инвентарь пакетов не перечитывается
  на такте процессов; планировщик тикает часто, решает `pipeline._due`.
- **Водяной знак материализации хранить явно.** Выводить его из `max(seq)`
  таблицы нельзя: нормализация законно отбрасывает строки (json_valid), и одна
  битая строка заставляла движок вечно «догонять» и слать пуши.
